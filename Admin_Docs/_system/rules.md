AI 근거용 — 사용자는 안 읽어도 됨

# Admin_Docs 작성 규칙

## 절대 규칙
1. 사용자 작성 칸(서비스 소개, 설계 의도, 리뷰 최종 판정, 면접 답, 사용자가 정할 질문의 답)은 AI가 지어내지 않는다.
   - ⚠️ 이 프로젝트 예외(2026-11-22 사용자 위임): 사용자가 "묻지 말고 AI가 답하고 검토하고 처리하라, 배포 때만 부르라"고 지시함.
     그래서 이 칸들은 agora-design.md(사용자가 확정한 기획 문서)에서 가져와 채우고, 칸 옆에 `(AI 대리 작성 — 사용자 위임)`을 붙인다.
     `(사용자 확인)`은 사용자가 실제로 승인한 칸에만 붙인다. 배포 때 대리 작성 칸 목록을 사용자에게 넘긴다.
2. 민감 정보 금지: API 키, 비밀번호, 토큰, .env 값, DB 접속 정보, 개인정보(실명·연락처·주소·이메일)는 문서와 커밋 메시지에 쓰지 않는다. 이름만 쓴다(예: "환경변수 GEMINI_API_KEY 사용").
3. Admin_Docs는 레포에 커밋한다.
4. 모든 문서는 2층(한눈에 보기 / 개발자 상세). STATUS·OPEN_QUESTIONS는 표 한 층.
5. 한 항목 5줄 이하. 위층에 쓴 전문 용어는 glossary.md에 추가.
6. 표시는 START_HERE의 표시 범례만 쓴다. 상태 칸에 [위험]·[주의]를 쓰지 않는다.
7. 이모지는 💡 ❓ ⚠️ 만.
8. 문서와 코드가 다르면 어느 쪽이 의도인지 먼저 묻는다(이 프로젝트에선 OPEN_QUESTIONS에 적고 agora-design.md를 기준으로 임시 판단).
9. 디자인(색·간격·폰트·컴포넌트 모양·반응형·접근성·색 대비)은 다루지 않는다.
10. 리뷰어는 레포 전체를 탐색하지 않는다. 리뷰 패킷 기준.
11. 사용자가 정할 선택은 추측으로 정하지 않고 OPEN_QUESTIONS에 적는다. 되돌리기 쉬운 쪽으로 임시 진행하고 그 사실을 적는다.
12. STATUS [됨]은 확인 방법이 있을 때만.
13. "내가 할 일" 블록이 있는 문서를 고칠 때마다 블록도 맞춘다.

## 문장 정리사
사용자 말을 다듬을 때: 말하지 않은 내용·이유·예시를 덧붙이지 않고, 판단의 세기를 바꾸지 않고, 쓰지 않은 전문 용어로 바꾸지 않는다. 맞춤법·어순·중복만 정리한다.

## 확신 표시 기준
- [확실]: 해당 코드를 직접 읽고(패킷 diff 또는 직접 연 파일) 확인. 테스트 실패처럼 결과로 드러난 것도 [확실].
- [추정]: 일부만 보고 판단, 관련 파일을 열지 않음, 실행해 봐야 알 수 있음. "무엇을 확인하면 [확실]이 되는지"를 적는다.

## STATUS 상태 기준
- [됨]: 완료 기준 충족 + 확인 방법(테스트 통과·직접 실행·리뷰 [통과] 중 하나 이상). 리뷰만 있으면 "실행 확인 없음" 병기.
- [일부]: 진행 중이거나 일부만 되거나 확인 방법 없음.
- [다음]: 시작 전. 리뷰가 [막힘]이면 [됨] 불가.

## 질문 규칙
- 누가 정해야 하나: 사용자 / 공부 / AI 확인. "사용자" 질문은 [열림] 표 맨 위.
- "AI 확인" 질문은 AI가 다음 작업 때 확인해 닫는다. 디자인 질문은 적지 않는다.

## 민감 정보 금지 목록
API 키, 비밀번호, 토큰, 세션 시크릿, .env 값, DB 접속 문자열, OAuth 클라이언트 시크릿, 개인정보(실명·이메일·연락처·주소)

## 범위 밖
⚠️ 디자인(색·간격·폰트·컴포넌트 모양·반응형 레이아웃·접근성·색 대비)은 검수 범위 밖이다. 사용자가 직접 평가한다.
⚠️ 배포, 서버 인프라, CI는 현재 검수 범위 밖이다. 실제 배포를 시작하면 R5 배포·운영 리뷰어(환경 분리, 로그, 모니터링, 롤백)를 추가한다.
